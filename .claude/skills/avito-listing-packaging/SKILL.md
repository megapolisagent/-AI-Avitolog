# Avito Listing Packaging

## Принцип

Данные о своём лоте — только те, что реально даны (файл в `data/lots/`). Данные о рынке и конкурентах — из штатного набора источников (`CLAUDE.md` §2: Apify, открытые сайты застройщиков, официальный API) или из материалов, переданных вручную (`data/market_raw/`). Ничего не досочиняется сверх того, что реально получено тем или иным путём — нет данных, это так и говорится (`CLAUDE.md`, §8).

**Перед любым вызовом Avito API** — сверься с `knowledge/agents_architecture.md` («Чек-лист роутинга»): какой справочный файл читать и какому субагенту (или скрипту) отдавать задачу под конкретный сценарий. Это живой, актуальный документ, не история — держит правило в одном месте, не в памяти агента.

**Объект от застройщика (первичка, ДДУ)** — операционный регламент CMO целиком (роли, 7 этапов, группы допуска застройщика, юридическая база 214-ФЗ/38-ФЗ, обязательный юридический блок карточки, стоп-критерий бюджета) — `references/avito-operating-playbook.md`. Раздел «Привязка к пайплайну» там же честно называет, что из регламента уже реализовано в этом доме, а что пока пробел (согласование Группы 2, проверка юрблока, стоп-критерий) — не считать эти пункты автоматически закрытыми только потому, что регламент существует.

## Единый пакет по подтверждённому лоту (главный путь)

Вход — один файл по шаблону `data/lots/TEMPLATE.md`: данные лота (ЖК, планировка, площадь, этаж, цена, ипотека/рассрочка, ПВ) + портрет покупателя (сегмент: семья/инвестор/наличные — боль, что реально убеждает именно этого человека). Без портрета покупателя текст выходит шаблонным («квартира в продаже») — портрет обязателен, не опция; если не дан — спросить, не писать нейтрально «на всех».

Выход — один пакет, все шесть частей обязательны за один прогон, каждая — своим фокус-скиллом, ты дирижируешь порядком, не пишешь текст/цифры сама:
1. **Финансовый расчёт** — `listing-fin-offer/SKILL.md` первым: цена/ПВ/платёж по реальным условиям застройщика, детерминированным кодом.
2. **Заголовок и геопривязка** — `listing-seo-geo/SKILL.md`: под поисковые подсказки Avito + район/метро.
3. **Карточка объявления + ТЗ на карусель + автоответ** — `listing-copywriter/SKILL.md`: берёт готовые цифры из шага 1 и заголовок из шага 2, пишет текст, ТЗ на фото, скрипт чат-воронки. Лид-магнит — под сегмент покупателя, банк форматов в `lead-magnets/SKILL.md`.
4. **Чек-лист модерации** — «Финальный валидатор» ниже, отмечено пройдено/не пройдено по каждому пункту.
5. **Строка KPI** — одна строка в формате `workspace/kpi-tracker.md` (создать файл, если его ещё нет), добавляется туда же, не только выводится в ответ.

Критерий готовности пакета — не «все разделы заполнены», а «владелец может опубликовать это сегодня без правок»: конкретные числа, не плейсхолдеры там, где данные в файле лота есть; честный `[УТОЧНИТЬ]` только там, где данных в файле реально нет.

## Карточка, заголовок, финансовый расчёт — три фокус-скилла (было Модулем 1, разбито по Правилу 3 Anthropic, 2026-09-10)

Порядок вызова: `listing-fin-offer` (цифры) → `listing-seo-geo` (заголовок+гео) → `listing-copywriter` (текст, ТЗ на карусель, чат-воронка). Каждый — самостоятельный SKILL.md со своим входом/выходом и правилом «не делает: …», не пересказывается здесь повторно. Бриф от `pain-point-extractor` (`workspace/<ЖК>-<дата>-brief.md`), если `market-recon` уже запускался по этому ЖК — обязательный вход для `listing-copywriter`, не для этого файла.

**Лот от застройщика (первичка, ДДУ)** — структура брифа и разделение ролей с CMO зафиксированы отдельным постоянным стандартом: `references/developer-listing-brief.md`. Финальный рычаг убеждения и JTBD-гипотезу CMO присылает готовыми, ты их не придумываешь на месте.

## Медиаплан продвижения — отдельный фокус-скилл (было Модулем 2, разбито по Правилу 3 Anthropic, 2026-09-14)

Пул карточек под объект (сколько держать одновременно, по каким осям) и логика платных форматов/времени запуска — `media-plan/SKILL.md`. Своя ставка CPA/CPX по формату считается не там, а субагентом `traffic-manager` — `media-plan` вызывает его, не пересчитывает сам. Не пересказывается здесь повторно.

## Финальный валидатор перед выдачей карточки

Закрытый чек-лист по правилам, подтверждённым официально (`knowledge/avito-platform-mechanics.md`) — не суждение, поэтому считает `tools/validate_listing.py`, не проза (найдено независимым аудитом 2026-09-10 — ровно тот же класс риска, что уже закрывался для платежа по ипотеке `listing-fin-offer/tools/calculate_payment.py`):

```
python3 .claude/skills/avito-listing-packaging/tools/validate_listing.py <путь к JSON со входом>
```

Вход — `price_field_value`/`full_price` (правило 1: в поле «Цена» только полная стоимость, ПВ/платёж — только в тексте), `listing_text` (правило 2: нет телефона/внешних ссылок), `floor_input`/`floor_in_text` (правило 3: этаж не искажён и не выдуман, если данных нет), `confirmed_percent_facts` (правило 4, best-effort: проценты в тексте сверяются со входными данными лота — несовпадение уходит в `needs_review`, не автоматический провал, скрипт не понимает смысл фразы). Схема — `INPUT_SCHEMA` в файле.

Скрипт возвращает `verdict`+`passed`+постатейный `checks` — взять `verdict` и любые `fail`/`needs_review` пункты в ответ владелице, не пересчитывать чек-лист заново текстом.

Не входит в валидатор (проверено и отклонено как непроверенное): списка запрещённых слов вроде «гарантированный доход» у Avito официально нет — не отказывать в таких формулировках только по этому основанию.

## Разведка рынка — отдельный фокус-скилл (было Модулем 5, разбито по Правилу 3 Anthropic, 2026-09-14)

Задача → три субагента/скрипта (market-analyst → market_snapshot_analyzer.py → pain-point-extractor) → аудит по 6 пунктам → рекомендация простым языком, таблица следом — `market-recon/SKILL.md`. Регламент сырой выгрузки живёт там же (`market-recon/references/market-raw-data-regulation.md`), не пересказывается здесь повторно.
