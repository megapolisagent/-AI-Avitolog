# Avito Listing Packaging

## Принцип

Данные о своём лоте — только те, что реально даны (файл в `data/lots/`). Данные о рынке и конкурентах — из штатного набора источников (`CLAUDE.md` §2: Apify, открытые сайты застройщиков, официальный API) или из материалов, переданных вручную (`data/market_raw/`). Ничего не досочиняется сверх того, что реально получено тем или иным путём — нет данных, это так и говорится (`CLAUDE.md`, §8).

**Перед любым вызовом Avito API** — сверься с `knowledge/agents_architecture.md` («Чек-лист роутинга»): какой справочный файл читать и какому субагенту (или скрипту) отдавать задачу под конкретный сценарий. Это живой, актуальный документ, не история — держит правило в одном месте, не в памяти агента.

## Единый пакет по подтверждённому лоту (главный путь)

Вход — один файл по шаблону `data/lots/TEMPLATE.md`: данные лота (ЖК, планировка, площадь, этаж, цена, ипотека/рассрочка, ПВ) + портрет покупателя (сегмент: семья/инвестор/наличные — боль, что реально убеждает именно этого человека). Без портрета покупателя текст выходит шаблонным («квартира в продаже») — портрет обязателен, не опция; если не дан — спросить, не писать нейтрально «на всех».

Выход — один пакет, все шесть частей обязательны за один прогон, каждая — своим фокус-скиллом, ты дирижируешь порядком, не пишешь текст/цифры сама:
1. **Финансовый расчёт** — `listing-fin-offer/SKILL.md` первым: цена/ПВ/платёж по реальным условиям застройщика, детерминированным кодом.
2. **Заголовок и геопривязка** — `listing-seo-geo/SKILL.md`: под поисковые подсказки Avito + район/метро.
3. **Карточка объявления + ТЗ на карусель + автоответ** — `listing-copywriter/SKILL.md`: берёт готовые цифры из шага 1 и заголовок из шага 2, пишет текст, ТЗ на фото, скрипт чат-воронки. Лид-магнит — под сегмент покупателя, банк форматов в `lead-magnets/SKILL.md`.
4. **Чек-лист модерации** — «Финальный валидатор» ниже, отмечено пройдено/не пройдено по каждому пункту.
5. **Строка KPI** — одна строка в формате `workspace/kpi-tracker.md` (создать файл, если его ещё нет), добавляется туда же, не только выводится в ответ.

Критерий готовности пакета — не «все разделы заполнены», а «владелец может опубликовать это сегодня без правок»: конкретные числа, не плейсхолдеры там, где данные в файле лота есть; честный `[УТОЧНИТЬ]` только там, где данных в файле реально нет.

## Карточка, заголовок, финансовый расчёт — три фокус-скилла (было Модулем 1, разбито по Правилу 3 Anthropic, 2026-09-10)

Порядок вызова: `listing-fin-offer` (цифры) → `listing-seo-geo` (заголовок+гео) → `listing-copywriter` (текст, ТЗ на карусель, чат-воронка). Каждый — самостоятельный SKILL.md со своим входом/выходом и правилом «не делает: …», не пересказывается здесь повторно. Бриф от `pain-point-extractor` (`workspace/<ЖК>-<дата>-brief.md`), если Модуль 5 уже запускался по этому ЖК — обязательный вход для `listing-copywriter`, не для этого файла.

## Модуль 2 — Медиаплан продвижения

Вход: ЖК/локация, число доступных планировок, бюджет (если дан).

Выход:
- Сколько карточек имеет смысл держать одновременно на объект — по осям: разные планировки (1-к/2-к евро/видовые), разные ценовые пороги (входная цена за м² / минимальный платёж по субсидии / полная стоимость — это разные карточки, не один текст), разные акценты (для жизни / для инвестора / семейная ипотека).
- Логика по платным форматам (x2–x10, XL) и времени запуска — с явным маркером ПРЕДПОЛАГАЮ/ЗНАЮ, см. `knowledge/avito-platform-mechanics.md` (пакеты не проверены Engineer напрямую).
- **Ставка CPA/CPX по конкретному лоту (поднять/снизить), и стоит ли вообще включать VAS с учётом текущих цифр кампании** — не считать самому, звать субагента `traffic-manager` (`.claude/agents/traffic-manager.md`) с реальными цифрами лота (текущая ставка, расход, CPA/CPL, целевой порог). Этот модуль отвечает за стратегию пула карточек и формат, `traffic-manager` — за число (ставку/бюджет) под конкретный формат.
- **Анти-дубликат (ЗНАЮ, `knowledge/avito-platform-mechanics.md`).** Несколько карточек на одну планировку разрешены Avito, только если у каждой реально свой текст и своё фото — не один шаблон с разными подставленными цифрами. При выдаче пула карточек — не просто менять цену/акцент в одном и том же тексте, переписывать заголовок и первый экран по-разному под каждый оффер.
- Если бюджет не дан — не выдумывать сумму, спросить или дать логику без привязки к рублям.

## Финальный валидатор перед выдачей карточки

Закрытый чек-лист по правилам, подтверждённым официально (`knowledge/avito-platform-mechanics.md`) — не суждение, поэтому считает `tools/validate_listing.py`, не проза (найдено независимым аудитом 2026-09-10 — ровно тот же класс риска, что уже закрывался для платежа по ипотеке `listing-fin-offer/tools/calculate_payment.py`):

```
python3 .claude/skills/avito-listing-packaging/tools/validate_listing.py <путь к JSON со входом>
```

Вход — `price_field_value`/`full_price` (правило 1: в поле «Цена» только полная стоимость, ПВ/платёж — только в тексте), `listing_text` (правило 2: нет телефона/внешних ссылок), `floor_input`/`floor_in_text` (правило 3: этаж не искажён и не выдуман, если данных нет), `confirmed_percent_facts` (правило 4, best-effort: проценты в тексте сверяются со входными данными лота — несовпадение уходит в `needs_review`, не автоматический провал, скрипт не понимает смысл фразы). Схема — `INPUT_SCHEMA` в файле.

Скрипт возвращает `verdict`+`passed`+постатейный `checks` — взять `verdict` и любые `fail`/`needs_review` пункты в ответ владелице, не пересчитывать чек-лист заново текстом.

Не входит в валидатор (проверено и отклонено как непроверенное): списка запрещённых слов вроде «гарантированный доход» у Avito официально нет — не отказывать в таких формулировках только по этому основанию.

## Модуль 5 — Разведка рынка (задача → субагенты → правила)

Вход: целевой ЖК + локация + комнатность (не весь ЖК разом). Готовый файл выдачи не обязателен — штатный запуск по запросу, не опция «если принесут».

**Полная цепочка — три шага, три разных исполнителя, каждый со своим контрактом:**

1. **`market-analyst`** (`.claude/agents/market-analyst.md`, вызов через `Agent`) — собирает две таблицы: А (топ-10 конкурентов-новостроек в локации + 2 смежные территории, тот же класс/метраж) и Б (целевой ЖК целиком — первичка и вся вторичка). Классифицирует продавца и ремонт, тянет текст объявления в таблицу сразу. Не оценивает, не рекомендует — правила и юридическая граница (`knowledge/apify-competitor-scraping-scope.md`) уже внутри его файла, не пересказывать здесь повторно.
2. **`scripts/market_snapshot_analyzer.py`** (детерминированный код, не агент) — считает то, что не требует суждения: дедупликацию вторички, цену мин/медиану/макс, «подозрительно занижено», «устарело» (только вторичка). Пороги — `config.json`, не в коде и не в голове агента.
3. **`pain-point-extractor`** (`.claude/agents/pain-point-extractor.md`, вызов через `Agent`, после шага 1) — берёт тексты из обеих таблиц, отдаёт бриф (боли + рычаг убеждения + формула подачи + ключевая эмоция) в `workspace/<ЖК>-<дата>-brief.md`. Это обязательный вход для `listing-copywriter`, когда есть данные конкурентов — не пропускать молча.

**Если файл уже дан** (`data/market_raw/`, сохранённая выдача) — субагентов заново не вызывать, прогнать скрипт напрямую по этому файлу; `pain-point-extractor` всё равно вызывается отдельно, если нужен бриф под текст.

**Формат таблиц — фиксированный, не придумывается заново каждый раз.** Ровно то, что отдаёт `render_markdown_table()` в скрипте — редактировать колонки только через отдельное решение владелицы, не по ходу разбора.

Дальше, поверх готовых таблиц — аудит по 6 пунктам на каждое объявление (это делает основной агент, не субагенты — нужен контекст лота владелицы для сравнения):
1. Заголовок — чем цепляет (цена/скидка/локация/УТП).
2. Первые 3 строки описания — какой триггер там главный.
3. Тип цены — реальная стоимость или заниженный платёж по ипотеке/рассрочке.
4. Финансовые триггеры — рассрочка 0%, транши, субсидия, трейд-ин, «только сегодня».
5. Визуальные крючки — что на обложке (если данные содержат описание фото, не только текст).
6. Пробелы — чего у конкурентов нет вообще → это место для УТП владельца.

**Итог — сначала рекомендация простым языком, таблица подкрепляет её, не заменяет.** Первым — 3-5 пунктов: с какой ценой, финансовым расчётом (`listing-fin-offer`) и стратегией продвижения (Модуль 2) заходить в выдачу и почему, без цифр из 12 колонок таблицы в этих пунктах — только вывод. Таблица целиком — следом, как подтверждение цифрами, не первым, что видит владелица. Раздатый голый расчёт без прочитанного вывода — не выполненная задача, тот же принцип, что `.claude/rules/direct-response-policy.md` («главный ответ — в тексте, не по ссылке»), только применённый не к каналу доставки, а к языку внутри самого текста. Рекомендация — вход для решения владелицы: сам не публикует лот и не меняет цену по своей инициативе (`CLAUDE.md` §3, §8).
